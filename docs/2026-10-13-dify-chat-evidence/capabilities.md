# 研究：Dify Chatflow / Agent 能力与版本边界

安琳，本次为只读能力研究，检索日 **2026-10-13**。未访问 `.env`、密钥、数据库、运行日志；未调用实例账号，未启动、升级或修改服务。主仓库已有大量脏改动，未改动项目文件。本报告只交付能力事实、可行接口路径和升级前提，最终业务架构及版本采用由主任务决定。

## 请求类型与直接结论

综合能力与实现参考核验。升级后的 **Chatflow + 经典 Agent 节点，入口 `/v1/chat-messages`** 能同时提供多轮会话、自主只读工具调用、显式分支、会话变量和结构化结果后处理；现有 0.15.3 做不到这个组合，因为没有 Agent 节点。Legacy Agent Chat 自主工具能力存在，但不能在它后面直接配置同一张 Chatflow 的校验分支。[D1][S1][S7]

**可供升级设计锁定的候选是 Dify 1.17.1，固定 SHA `8387590ace4a094de812b7847fc6a4c3a27cd52b`**：官方 release API 返回 2026-09-10 发布、`prerelease=false`、`draft=false`。这是检索时的稳定候选，不代表本环境已经完成兼容性或运行验收。不要以移动 `latest` 作为部署契约；不要把 2026 年 Beta 新 Agent 当成经典 Agent 节点。[R1]

## 会话、输入和记忆的真实语义

- **新会话**：不带 `conversation_id` 或空字符串；保存响应返回的 ID，后续继续带该 ID 与相同 `user`。`user` 是应用定义的终端用户标识，Dify API Key 是应用凭据；二者不是同一身份。[D2]
- 0.15.3 按 `conversation_id + app_id + from_end_user_id` 查会话，找不到报错。`user` 应由可信后端生成/映射，不能让浏览器任填。相同 `user` 可以拥有多个 conversation；不能仅凭 `user` 自动把五人的业务状态合并。[S1]
- 0.15.3 的 Chatflow、Chat、Agent Chat 都复用首轮 `conversation.inputs`，所以第二轮把行情/目标/权限塞回 `inputs` 无效。1.17.1 的 Chatflow 和 Legacy Agent 已改为每轮 `_prepare_user_inputs(args.inputs, app_config.variables, ...)`。**新版本传本轮完整 inputs，不把它当任意变量 PATCH 接口。** [S1][S2][S6]
- 1.17.1 Chatflow 的 `app_generator.py:165-175` 还存在：Service API 查不到给定 conversation 时按新会话继续的分支。不能假设“不存在 ID 必定 404”，后端须核对实际返回 conversation ID；该行为仅做源码静态确认。[S6]
- **会话历史与会话变量是两种存储**。历史是 user/assistant 轮次，按消息数、token 预算裁剪；不会自动形成跨会话人物画像。Chatflow LLM/Agent 节点必须配置 Memory；会话变量则需变量赋值节点写入，写入后后续轮次读取。[D4][D5][S3]
- 本地 `TokenBufferMemory` 最多查询 500 条，默认 token budget 2000，并裁剪最旧 prompt；不要承诺全历史无损记忆。1.17.1 经典 Agent 的 runtime_support 仅在 `node_data.memory` 存在时读取历史。长期关系记忆、事实时效与跨会话复用需另有明确持久化契约；Dify 的 conversation ID 不自动完成这些工作。[S3][S7]
- 新版 PUT 会话变量要求先有会话及 variable ID，类型必须匹配；没有证据表明该 PUT 与下一次 `/chat-messages` 是原子事务，也没有业务版本 CAS 契约。每轮新上下文优先依靠已核实的新版本请求 inputs 或轮内只读工具获取；若使用 PUT，应在主任务设计中处理同会话并发顺序。[D3][S8；末句为设计推论]

## 工具参数绑定、五人隔离与 Authorization

**结论：可以变量绑定，但不能把“手动参数”当成不可绕过的授权边界。**

1. 1.17.1 `runtime_support.py:93-109`：`auto=0` / `ParamsAutoGenerated.CLOSE` 会按 selector 从 variable pool 读取值，可引用 Start 输入或 conversation 变量；`:153-166` 把这些参数改为 `FORM` 并放入 `runtime_parameters`。这证明 `turn_id/context_ref` 不必靠模型生成。[S7]
2. 但当前官方 **Dify Agent Strategies 0.0.50**（上游固定 SHA `3b4e77c0be57dfcdde48183243fef411664e8755`）的 Function Calling 实现 `function_calling.py:537-544` 使用 `{**tool_instance.runtime_parameters, **tool_call_args}`，模型返回同名额外参数时后者覆盖前者。它还把合并后的参数放到工具日志 `:647-654`。[P1]
3. 反向调用 `backwards_invocation/tool.py:34-46` 重新获取工具 runtime；`tool_manager.py:503-534` 从收到的合并参数构建 FORM 值，没有原 Chatflow 绑定值可供恢复。通用 Tool.invoke 虽然会再用 runtime 覆盖同名参数，但**不能恢复这条插件路径里已被覆盖的原值**。[S9]
4. 因此只支持如下安全表述：手动参数正常不由模型填写；真正的权限必须由工具后端验证。短期 capability 可绑定本轮输入，服务端从它解析可信 trader/turn/context/允许操作，拒绝伪造、过期、重放以及矛盾的独立 trader_id。该项是基于调用链的工程推论，不是 Dify 提供的“五人隔离保证”。[S7][S9][P1]
5. OpenAPI custom tool 的 provider Authorization 使用存储的 credential，`custom_tool/tool.py:91-116` 没有 Start 变量模板求值；**不能宣称 provider secret 自身支持每轮动态模板**。但同文件 `:200-213` 会把 OpenAPI `in: header` 参数写入 HTTP header，所以可声明独立 `X-Turn-Capability` 并用手动变量绑定。[S9]
6. 同名 OpenAPI header 在 credentials header 之后赋值，可覆盖此前 Authorization；避免把可生成参数和静态认证放在同名 header。动态手动参数仍可落到节点/插件工具日志，不能称“对 Dify 运维或日志绝对隐藏”。能力凭证不能放进对外回复，也不应由模型读到整个原始值。[S9][P1]

当前 Agent 文档把 `auto: false` 写成自动生成，和固定 tag 的 `CLOSE=0` 实现相反；此处采用源码与待验收 DSL，而非文档该句。[D6][S7]

## Agent 后取得结构化方案，而非直接外发

**真实可行的节点组合示例**：`Start → 可信上下文读取 → 经典 Agent（仅搜索券/相似券/发行人/计算器等只读工具）→ LLM（结构化 schema）→ Code（校验并序列化）→ If/Else → Answer（仅机器 JSON）`。这是能力级示例，不是完整业务设计；整轮依然由 `/chat-messages` 驱动。

- 经典 Agent 输出是 `text`、`usage`、`files`、`json` 及插件自定义变量。其 `json` 是日志列表和插件发出的 JSON 消息混合体，**不是默认满足 action/trader_state schema 的业务对象**。[S10]
- 结构化 LLM 可以把 Agent 的文本及经过裁剪的事实结果转成一个明确对象，例如 `proposed_action`、`reply_draft`、`proposed_trader_state`、`evidence_refs`、`requires_review`。字段只是示例；结构格式正确不证明事实、权限或保密条件正确。官方明确说明非原生 JSON 模型可能仅靠提示词约束、结果有差异。[D4][S11]
- Code 可以接对象进行确定性字段/枚举校验，并用标准 JSON 序列化器返回一个字符串；不建议手写模板拼接未转义的模型字符串。只让 Answer 引用**校验后序列化字符串**，不要引用 Agent.text 或未完成的 LLM.text。[D7][D8]
- Answer 只定义 Chatflow 返回给调用方的内容，不必接真实 IM 发信工具。后端应缓冲完整机器 JSON，独立检查业务规则、授权、敏感字段，再决定允许展示/发送的具体文本；`agent_log/node_finished` 等内部事件不得转发给交易对手。[D1][D7；后端门为安全推论]
- `proposed_trader_state` 应先作为提议返回；不能把模型自报“允许成交/允许泄露”等布尔值当授权。若 Chatflow 已把拟议状态写入会话变量，而后端最终拒绝，应定义状态一致性处理；Dify 变量赋值不与后端放行原子提交。[S3][S8；推论]

## 流式事件、停止与可观察性限制

- 接入须区分 `task_id`（本次停止用）、`conversation_id`（多轮会话）与 `workflow_run_id`（Chatflow 本轮执行记录）。Chatflow 的 SSE 可以出现 `workflow_*`，这不代表调用入口变成独立 `/workflows/run`。[D1][D9]
- Legacy Agent 的 `agent_thought` 带 tool/input/observation；经典 Agent 节点的新事件为 `agent_log`，并有层级日志。二者均不等于安全可外发文本。[S4][S10]
- 0.15.3 和 1.17.1 的 Chatflow Service API 简化转换均会对 `node_started/node_finished` 清掉 inputs/process_data/outputs 等详情。不能依赖每个 `node_finished.outputs` 从 API 抓到结构化决策；使用明确的最终机器 JSON 契约。[S4][S12]
- HTTP 200 不证明成功，SSE 内仍会出现 error 或失败的 workflow_finished。新文档列出 Chatflow 终止事件与断线续流能力，但本轮未对每个运行版本验证事件顺序，客户端宜按标识收集必要成功终态，不能对旧版套用新版顺序。[D9]
- `/chat-messages/{task_id}/stop` 配相同 user 是停止生成接口。0.15.3 实现只设置 stop flag；无效/非所属 task 也可能返回 success，不能据此声称确已停掉所有下游工作。**停止不是撤销已执行工具的事务回滚**。[S5][D10]

## 升级候选与官方迁移边界

**最低能力门槛**：Chatflow 经典 Agent 节点、可用且锁版的 Agent Strategy / 模型插件、每轮输入更新、显式会话变量持久化、结构化结果后处理、可观测成功/失败/停止、后端拒绝越权工具调用。1.0.0 是官方引入插件与 Agent 节点的历史起点，**并不能由此推出 1.0.0 已满足全部门槛**。[R2]

候选 1.17.1 已静态核实上述主要接口/节点面；采用前仍应在隔离环境锁定 Dify tag、镜像 digest、插件版本和模型版本，做能力验收。这里不提供“可直接原地升级”的结论。

官方迁移材料支持以下检查阶段：

1. **0.x → 1.x 插件迁移阶段**：1.0.0 release 要求提取旧模型/工具、先安装对应插件，再数据库 schema 迁移；`migrate-data-for-plugin` 会改旧 provider 标识，官方要求确认不回退再执行、并先备份。历史详解链接已 404，当前可复用的一手依据是 1.0.0 release 正文；不能默默照抄失效文档或假设旧 CLI 在 1.17.1 原样存在。[R2]
2. **数据与运行组件迁移阶段**：1.17.1 将 pre-1.15 legacy 模型类型规范化纳入数据库迁移，release 标明不可逆，回退须依靠完整可恢复备份；不是换回旧镜像即可。[R1]
3. **条件性 Weaviate 迁移阶段**：若使用已有数据的 bundled Weaviate，1.17.1 的默认服务器从 1.27.0 跳到 1.39.2，官方要求逐 minor 升级；更旧服务器/旧客户端先按 v4 迁移指南。新空部署、其他向量库不套用此阶梯。本轮没有读取环境或数据库，所以不能判断本机是否命中。[R3][R4]
4. **策略准备与验收阶段**：锁定官方 Agent Strategy、所选模型 provider、只读 OpenAPI 工具契约。当前上游策略 manifest 0.0.50 声明 `minimum_dify_version: 1.7.0`；这只是最低声明，不是本环境对 1.17.1 的实测兼容证明。[P2]
5. 1.17.1 release 提到 Agent V2 启用后经典 Agent 节点可能从选择器隐藏，已有经典图发布问题在该版修复。必须验收目标环境能新增/导入/发布所需经典 Agent 图，不能因文档展示了节点就认为当前配置可创建。[R1]

本轮不执行上述任何迁移动作。升级采用和中间版本演练路线仍需依赖评估与部署验收；这里只给可追溯候选及必要的不可跳过阶段。
