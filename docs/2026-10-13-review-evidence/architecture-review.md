## 已证实问题

### A1 · P1：停止机器人不能阻止真实自动发送

**证据**：`mock/mock_server.py:978-1015` 的监控 GET 经 `_real_screen` 调用 `sync_live`；`imlink/dify_inquiry.py:542-553` 启动 Dify 并发送回复。停止接口 `mock/mock_server.py:1070-1077` 仅修改 `BOT`，发送链不读取该状态。`web/src/pages/Monitor.vue:44-46` 每 3 秒继续刷新监控。

**触发与后果**：已配置 Dify 和 OSS 时，点击停止后监控轮询仍可触发外发；没有用户看页面时则没有同等稳定的消息处理驱动。

**整改**：GET 保持只读；消息处理移到独立后台任务。全局停止状态持久化，在调用模型前和实际投递前检查。

**验收**：停止期间持续查询监控、注入新入站及在途模型结果，外发次数均为零；关闭浏览器不影响已授权任务处理。

**证据等级**：代码链路证实；没有执行真实发送。

### A2 · P1：人工接管存在竞态，交回机器还会处理旧消息

**证据**：`imlink/dify_inquiry.py:349` 只在调用模型前查暂停；`389-397` 收到结果后直接启动发送。消息在 `331-332` 按时间倒序处理；`imlink/inquiry_rules.py:269-283` 处理第一条新消息后清除等待标记，随后旧消息重新获准。`flush_replies`（`dify_inquiry.py:293-311`）也不复核会话暂停。

**触发与后果**：Dify 调用途中人工接管，模型结果仍会发送；交回后新消息先处理并清掉等待标记，同批旧消息继续调用模型。

**整改**：保留不可回退的接管时间/消息游标；任务捕获授权版本，投递前再次校验；缓存回复重试必须经过同一闸门。

**验收**：覆盖调用中暂停、缓存回复后暂停、交回后混合新旧消息、进程重启恢复。

**证据等级**：完全内存探针已复现。暂停期间 `sender_called=True`；交回后的新旧两条消息调用 Dify 2 次，预期只有新消息调用 1 次。

### A3 · P1：异步回复未冻结来源账号，切换通道可能用另一账号发送

**证据**：`imlink/monitor_feed.py:511-545` 读取后生成的消息没有保留工作台/账号；发送函数参数只有 `peer, text, msg_id`。`imlink/dify_inquiry.py:263-279` 发送时重新读取全局 `store.active()`。同文件 `33-42` 的标签主键优先只用消息 `id`。

**触发与后果**：账号 A 的模型调用执行期间切换为 B，发送结果使用 B 的命令身份，目标仍来自 A 的会话。不同账号相同消息 ID 也可能串标签缓存。

**整改**：入站、标签、会话、命令使用完整身份 `(workbench_id, account_uid, session_kind, peer_id, message_id)`；任务持有来源绑定快照，切换账号不能改写任务身份。

**验收**：阻塞 A 的模型调用，切换 B 后释放，禁止出现 B→A 对手的命令；两账号相同消息 ID 不串缓存。

**证据等级**：数据流证实；未执行真实账号切换/外发。

### A4 · P1：真实自动链绕过已有确定性谈价规则

**证据**：`imlink/dify_inquiry.py:45-52` 获取模型自由文本，`389-397` 直接交发送；出口只走词语红线。`relay/side_b/engine.py:76-129` 中的价格边界、追问量及实价转人工规则，只由旧邮件循环 `relay/side_b/run_b.py:17-29` 调用。词语闸见 `relay/side_b/phrase.py:38-68`。

**触发与后果**：模型返回不含禁词但越过价格边界的询价文本，真实链路没有数值规则阻止它。

**规格冲突**：`docs/06-dify-workflow.md:3-5,21-25` 要求模型只抽取、规则决定价格与动作。最新 014 未明确撤销该约束。实际外部 Dify 配置没有读取，因此不能断言已经发生越界报价；代码绕过规则本身确定。

**整改**：统一到一个规则服务；模型输出先做结构及归属验证，再决定动作和固定话术。

**验收**：覆盖 BID/OFR 镜像、越界、低置信、多券、实价及附加条件；直接注入越界模型输出不得外发。

### A5 · P1：同文历史回执可把失败询价误标成功

**证据**：`imlink/dify_inquiry.py:435-458` 仅按归一化正文匹配回执，没有验证账号、收件人、发送时间及命令状态。`imlink/rfq_status.py:69-79` 只按券保存一个状态。

**触发与后果**：相同报价发给不同对手，或重复发送同文报价时，一人的旧回执可把另一人的本次失败命令确认成功；部分失败被隐藏。

**整改**：回执关联 `cmd_id`；协议暂不提供时，至少采用账号、会话、正文摘要及时间窗联合匹配。券状态从各询价会话汇总，不能直接相互覆盖。

**验收**：不同收件人同文、同文重发、昨日回执、多收件人部分失败都不得互相确认。

**证据等级**：完全内存探针已复现：新账号/收件人的 `failed` 命令遇到另一账号/对手的同文历史回执，被升为“询价中”。

### A6 · P1：ACK 超时被终结为失败，迟到成功无法恢复

**证据**：`imlink/oss_send.py:225-228` 超时永久写 `failed`；`imlink/commands.py:148-149` 已有 ACK 或非 submitted 状态直接返回。回执 GET `imlink/routes.py:197-219` 只读本地状态和目录，不继续取真实 ACK。重新询价生成新 UUID（同文件 `317-319`）。自动回复还按全部历史命令正文去重，失败命令也阻止重试（`dify_inquiry.py:270-278`）。

**触发与后果**：指令上传且采集端已发出，但 ACK 迟到/读取失败，页面永久显示失败；重新询价可能重复外发。自动回复的失败重试则可能永远停在正文重复分支。

**整改**：区分待投递、已提交、结果未知、明确失败、已送达；持久对账及重试使用稳定命令 ID，未知结果不能简单提示重新发。

**验收**：上传成功后断网、ACK 迟到、服务重启、部分批次成功后重试，最终状态收敛且不重复发送。

**证据等级**：完全内存探针已复现：先超时失败再应用成功 ACK，结果仍为 `failed / ok=false`。

### A7 · P1（跨网部署）：OSS 接收仍依赖另一项目本地采集库

**证据**：`imlink/dify_inquiry.py:28,522-529` 读取 `QTRADE_AGENT_DB`，默认是另一项目的 `real-chain-20261010/agent.db`。本仓库 OSS 实现包含目录、通讯录、命令及 ACK，但没有装配消息对象消费者；`remember_messages` 只有定义及测试调用。缺库、SQL 错误转成空列表（`imlink/monitor_feed.py:493-521`），监控 API 仍返回成功（`mock/mock_server.py:1001-1021`）。

**触发与后果**：工作台和内网分机后，可以测试目录、发出指令，却收不到聊天及读库回执；接收故障被伪装为空屏。前端会用成功空结果替换原内容（`web/src/pages/Monitor.vue:130-143`），与 `docs/014-前端交互说明.md:73` 不符。

**整改**：补持久 OSS 入站消费者、账号游标和幂等落库；区分暂无消息与读取失败，本地采集库保留为显式联调适配器。

**验收**：不挂载外网采集库，只经假 OSS 完成双向链；中断读取后保留最后成功内容并展示错误。

**证据边界**：外部仓库是否有独立消息同步服务未核实；这是本仓库交付闭环缺口，不能据此断言所有部署均无接收能力。

### A8 · P2：JSON 业务状态没有共享事务保护，实例锁不能防止丢更新

**证据**：`imlink/routes.py:395-402` 每请求创建 `FloorBook/SessionGate`，对象各自建立实例锁（`imlink/inquiry_rules.py:105-108,168-175,194-196`）。`LabelBook` 无锁并由后台发送线程共同改写（`imlink/dify_inquiry.py:172-225,393-397`）。各文件使用固定 `.json.tmp`，命令/状态/处理标记分开提交。

**触发与后果**：并发修改底价、接管状态或模型标签会丢更新；固定临时文件还有替换竞争；进程在分文件提交之间退出后不能保证状态一致。

**整改**：优先把业务状态迁入当前可用的事务数据库，通过唯一键和事务维护会话、inbox/outbox。若临时保留文件，必须有按路径共享锁、进程边界及明确恢复协议。

**验收**：并发修改不同券及同会话；在每个提交边界模拟故障重启，状态和外部副作用可恢复且不重复。

**证据等级**：完全内存模拟实际读改写路径，两个实例并发设置不同券底价，最终仅留 1 条，预期 2 条。真实磁盘竞争未运行。

### A9 · P2：邮件模式有配置入口，没有对应传输实现

**证据**：`web/src/pages/Link.vue:9,156-165` 暴露邮件模式及 IMAP 参数；`imlink/routes.py:103-106` 仍用 HTTP `client.probe` 测试邮件；`imlink/store.py:104-107` 生成 `host:993`，随后拼 `/api/v1/system/health`（`imlink/client.py:152-163`）。`relay/mailbus.py:39-52` 是本地文件直投 PoC，不消费这些配置。

**触发与后果**：保存邮件模式后，测试/接收/发送无法按 UI 暗示的邮件链路闭环。

**整改**：未实现前明确不可用；如在当期范围，增加独立邮件适配器并接入共同会话与回执状态。

**验收**：用假 IMAP/SMTP 验证测试、收取、确认及失败恢复；不能用本地文件直投替代邮件验收。

## 整改顺序与取舍

1. **P1，先控制外发**：统一全局停止、会话接管、来源账号授权复核；移除 GET 外发副作用。范围局限入口和发送门，优先收益最大。
2. **P1，统一业务状态**：持久会话、入站游标、规则决策、命令 outbox 和回执关联进入共同事务边界；复用已有确定性规则，避免复制第三套规则。
3. **P1，补跨网与恢复**：实现 OSS 入站与后台 ACK 对账，处理未知结果和幂等重试；加入中断/重启恢复验收。
4. **P2，收敛入口**：补状态接口，明确邮件能力，更新能力矩阵/文档；保留现有 Vue/Python 分离，不重做前端状态库。

| 方案 | 收益 | 代价 |
|---|---|---|
| 现有 Python 服务内抽业务模块、后台任务及事务存储 | 改动可控，可复用规则与接口，适合当前规模 | 需梳理旧 JSON 数据迁移及任务生命周期 |
| 拆成多个微服务并同时迁移国产数据库 | 可独立部署扩容 | 增加跨服务一致性问题，且当前缺少客户环境信息 |

建议第一种。模块边界先稳定为：行情只提供数据；通道适配器负责收发及回执；业务服务拥有会话、授权和规则；HTTP/前端展示查询结果并提交明确命令。
