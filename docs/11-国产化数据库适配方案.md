# 后端与数据库适配方案 —— ODS + OceanBase / GaussDB

> 2026-09-19。南银理财现券询价项目。
> 现状:mock 用 SQLite 单机验证了管线（见 `09` / `10`）。本文讲**换成客户国产化基础设施要改什么**。
> ⚠️ 有一条会直接打掉当前设计，见 §2。

## 0. 先要回答的问题（挡住设计，必须先问客户）

| # | 问题 | 为什么挡路 |
|---|---|---|
| **Q1** | **ODS 是实时（CDC）还是批量（T+1 / 每 N 分钟）？** | 若是批量，**ODS 不能做实时行情的来源**，实时路径必须直连 OT/QT。这决定整个拓扑 |
| **Q2** | OceanBase 跑 **MySQL 模式还是 Oracle 模式**？GaussDB 是**集中式还是分布式（DWS）**？ | 决定 SQL 方言、序列行为、upsert 写法，三者都不通用 |
| **Q3** | 是否允许引入 **Redis / 内存中间件**？ | 决定热路径能不能不落库（§3）。若全栈信创只许用库，方案要大改 |
| **Q4** | 实时报价的**留存要求**：全量流水留多久？要不要可回放？ | 决定 `quote_flow` 是留在库里还是走归档 |
| **Q5** | 单表预估日增量、并发写入 TPS 上限、DBA 给的连接数配额 | 决定分区策略与批量提交粒度 |

**Q1 是最关键的。** 我按"ODS 批量、实时另走直连"设计，见 §1。如果 ODS 其实是 CDC 实时的，方案可以简化一层。

## 1. 目标拓扑

```
                 ┌──── 实时路径（毫秒级）────────────────────┐
OT / QT 报价源 ──┤                                          │
                 │  报价接入服务 ──► 内存热态 ──► WS 网关 ──► 浏览器
                 │   (分配 flow_id)    (最新态)
                 └──────┬───────────────────────────────────┘
                        │ 异步批量落库（不在关键路径上）
                        ▼
                 OceanBase / GaussDB
                   quote_flow（流水，分区）
                   quote_latest（最新态，可选）
                        ▲
                        │ T+1 / 定时
ODS ──── 静态主数据 ────┘
  （券基础信息、发行人、评级、内部意向）
```

**两条路径必须分开**：

- **实时路径**：报价源 → 接入服务 → 内存 → WS。**不经过数据库**。
- **持久化路径**：接入服务异步批量写库，用于审计、回放、对账。写库慢了不影响推送。

**ODS 只承担静态主数据**（券简称、评级、期限、发行人、内部意向指令）。这些东西 T+1 更新完全够用，正好对应契约里"推送只带动态字段、静态走缓存 join"的设计——**ODS 的批量特性和静态数据的低频特性天然吻合**。

## 2. ⚠️ 致命点：`flow_id` 在分布式库上不再单调

### 2.1 问题

当前 mock：

```sql
flow_id INTEGER PRIMARY KEY AUTOINCREMENT   -- SQLite 保证单调递增
```

契约把 `flow_id` 定成**行版本号**，前端靠 `d.f >= cur.f` 做 last-write-wins。**这依赖严格单调**。

但在国产分布式库上这个前提不成立：

| 库 | 自增/序列行为 | 后果 |
|---|---|---|
| **OceanBase**（MySQL 模式） | `AUTO_INCREMENT` 按租户/节点**分段缓存**，多 observer 并发插入时**返回值不保证全局单调** | 后插入的行可能拿到更小的 id |
| **OceanBase**（Oracle 模式） | `SEQUENCE` 默认 `CACHE 20`，同样分段 | 同上 |
| **GaussDB / openGauss** | `SERIAL` 底层是 sequence，带 cache；DWS 分布式下各 DN 独立取段 | 同上 |

**只要不单调，前端的版本比较就会把新价当旧价丢掉**——表现是"价格偶尔不更新"，而且极难复现、极难排查。

### 2.2 三个可选解，推荐第一个

**① 在接入服务分配（推荐）**

`flow_id` 不由数据库生成，由**单写入点的接入服务**分配：

```
flow_id = 自增计数器（进程内 AtomicLong）
启动时从库里取 MAX(flow_id) + 预留水位 恢复
```

- 优点：真正单调、零 DB 往返、与库无关（换库不受影响）
- 代价：接入服务必须是**单写入点**（或按券哈希分片，每片一个计数器——同一只券永远落同一片，跨片不可比但也不需要比）
- 重启恢复：取 `MAX(flow_id)` 后**再加一个安全水位**（比如 +100000），避免未落库的内存态造成回退

**② Snowflake 式 ID**

`(时间戳41位 | 节点10位 | 序号12位)`。单节点内单调，跨节点近似有序。
适合接入服务天然多活的场景。代价是 ID 变大（int64 仍够用），且跨节点严格比较无意义。

**③ 库序列 + `NOCACHE`/`ORDER`**

OceanBase Oracle 模式 `CREATE SEQUENCE ... NOCACHE ORDER`、GaussDB 类似。
**不推荐**：每次取号都要走一致性协议，几百 TPS 就会成为瓶颈，正好卡在我们的峰值区间。

> **决策**：用 ①，按 `bond_uni_code` 哈希分片。同一只券的版本比较永远在同一片内，满足前端语义；跨券不需要比较。

### 2.3 连带要改的地方

`docs/09` 契约 §1 里写的 `flow_id INTEGER PRIMARY KEY AUTOINCREMENT` 要改成**由应用写入的 BIGINT**，并在文档里写明"单调性由接入服务保证，不依赖数据库"。

## 3. 热路径不落库

### 3.1 为什么

峰值 300 条/秒的 upsert 打到分布式库上：

- OceanBase/GaussDB 每次写都要走 **Paxos/Raft 多数派**，单条延迟通常 2~10ms
- 300 TPS 的同步写会把接入服务阻在 IO 上，WS 推送延迟直接被数据库抖动绑架
- `quote_latest` 是**高频覆盖写**，对 LSM-Tree（OceanBase）而言会制造大量 compaction 压力

### 3.2 怎么做

| 数据 | 存哪 | 理由 |
|---|---|---|
| **最新态**（每券最新报价） | 接入服务**内存** Map；多活时用 Redis | 只有几千到几万只券，内存足够；这是推送和首屏的唯一数据源 |
| **流水**（每条报价） | 异步批量写库，**500ms 或 500 条**攒一批 | 审计/回放用，不在关键路径 |
| **静态主数据** | ODS → 启动加载进内存 + 定时刷新 | 低频，T+1 足够 |

若 **Q3 答案是"不许引入 Redis"**：单活部署用进程内存，主备切换时从 `quote_flow` 回放当日数据重建最新态（几十万条，秒级）。

### 3.3 首屏 REST 从哪来

`GET /api/bonds` 现在查 `quote_latest ⋈ bond_static`。改造后：

- **最新态从内存出**，静态从内存缓存出 → 不查库
- keyset 游标仍用 `flow_id`，内存里按 `flow_id` 倒序维护一个索引即可

这样列表首屏也不依赖数据库，DB 只在审计/对账时被查。

## 4. SQL 方言差异

即便热路径不落库，流水表和静态表仍要读写。三处不通用：

### 4.1 Upsert

```sql
-- SQLite（当前）
INSERT INTO quote_latest (...) VALUES (...)
ON CONFLICT(bond_uni_code) DO UPDATE SET ...
WHERE excluded.flow_id > quote_latest.flow_id;

-- OceanBase MySQL 模式
INSERT INTO quote_latest (...) VALUES (...)
ON DUPLICATE KEY UPDATE
  best_bid = IF(VALUES(flow_id) > flow_id, VALUES(best_bid), best_bid),
  ...,
  flow_id  = GREATEST(flow_id, VALUES(flow_id));
-- 注意:MySQL 模式没有 ON CONFLICT ... WHERE,守卫只能用 IF() 逐列写,啰嗦但可靠

-- OceanBase Oracle 模式 / GaussDB
MERGE INTO quote_latest t
USING (SELECT ? AS bond_uni_code, ? AS flow_id, ... FROM dual) s
ON (t.bond_uni_code = s.bond_uni_code)
WHEN MATCHED THEN UPDATE SET ... WHERE s.flow_id > t.flow_id
WHEN NOT MATCHED THEN INSERT (...) VALUES (...);

-- GaussDB（PG 兼容模式）
INSERT ... ON CONFLICT (bond_uni_code) DO UPDATE SET ...
WHERE EXCLUDED.flow_id > quote_latest.flow_id;   -- 与 SQLite 最接近
```

**做法**：把 `mock/db.py` 的 SQL 抽成 dialect 层，`upsert_latest()` 按方言出不同语句。现在集中在 `_UPSERT_SQL` 一处，改造成本不大。

### 4.2 自增/序列

见 §2，统一改成应用侧赋值，`flow_id BIGINT NOT NULL`，**不用数据库自增**。这反而消除了方言差异。

### 4.3 分页

keyset（`WHERE flow_id < ? ORDER BY flow_id DESC LIMIT ?`）三个库都支持，**不用改**。
Oracle 模式下 `LIMIT` 要写成 `FETCH FIRST n ROWS ONLY`。

## 5. 表结构调整

### 5.1 `quote_flow` 要分区

日增几十万、留存若干月，单表会很快到亿级。

```sql
-- OceanBase / GaussDB 都支持按范围分区
PARTITION BY RANGE (biz_date) (
  PARTITION p20260919 VALUES LESS THAN ('2026-09-20'),
  ...
)
```

加一列 `biz_date DATE`（业务日）做分区键，配合自动建分区脚本。
好处：按日归档/清理是 `DROP PARTITION`，秒级；不分区的话 `DELETE` 老数据会造成巨大 compaction。

### 5.2 OceanBase 特有：主键即聚簇

OceanBase 表按主键聚簇存储。`quote_flow` 主键若是 `flow_id`，按券查历史（`WHERE bond_uni_code=?`）就要回表。

建议主键 `(bond_uni_code, flow_id)`，把同一只券的流水物理聚在一起——按券回放是最常见的查询。全局唯一性由 §2 的分片计数器保证。

### 5.3 静态表来自 ODS

`bond_static` 不再由我们维护，改为**从 ODS 同步**：

- 建一个视图或同步任务，把 ODS 的券主数据落成我们契约 §1.1 的形状
- 字段映射表要单独维护（ODS 的字段名大概率和契约不一致）
- **同步频率 T+1 即可**，但要有"当日新券"的补拉通道——新发行的券当天就可能报价

## 6. 改造清单与工作量

| 项 | 改哪 | 预估 |
|---|---|---|
| `flow_id` 改应用赋值 + 分片计数器 | `mock/db.py` → 接入服务 | 中 |
| 抽 dialect 层（upsert / 分页 / 建表） | `mock/db.py` | 中 |
| 热态移到内存，DB 异步批量写 | 接入服务（新） | **大** |
| `quote_flow` 加 `biz_date` + 分区 | DDL | 小 |
| 主键改 `(bond_uni_code, flow_id)` | DDL | 小 |
| `bond_static` 改为 ODS 同步 | 新同步任务 + 字段映射 | 中 |
| 首屏 REST 改查内存 | 接入服务 | 中 |
| **前端** | **无改动** | **0** |

**前端零改动**是这套分层的直接收益——浏览器只认网关契约（`docs/10` §2），底下换成什么库它不知道也不需要知道。

## 7. 我还不确定、需要验证的

诚实列出，不要当成结论：

1. **OceanBase `AUTO_INCREMENT` 的具体非单调表现** 我是按分布式数据库的通用机制推断的（分段缓存），没有在客户的实际版本和部署形态上实测过。**上线前必须做一次并发插入验证**：多连接并发插 10 万条，检查返回的 id 序列是否有回退。
2. **GaussDB 的模式**（集中式 / DWS / PG 兼容度）差异很大，`ON CONFLICT` 是否可用要看具体版本。
3. **ODS 的实时性**（Q1）——整个 §1 拓扑建立在"ODS 是批量"这个假设上。
4. **信创环境的 Redis 可用性**（Q3）——不可用时 §3.2 的多活方案要换。
5. 峰值 300 条/秒是我们按"8 小时 30 万"推的，**客户实际峰值需要他们给**。如果峰值是 3000 条/秒，接入服务要重新设计（分片 + 多活）。

## 8. 建议的推进顺序

1. **先问 Q1~Q5**，尤其 Q1 和 Q3
2. 拿到客户一套测试库，**做 §7.1 的自增单调性验证** —— 这一条不验，后面全是空中楼阁
3. 抽 dialect 层，让 mock 能同时跑 SQLite 和目标库（本地开发仍用 SQLite）
4. 做接入服务的内存热态 + 异步落库
5. 接 ODS 静态同步
6. 用 `docs/10` §5 的验收指标表，在客户环境复测一遍
