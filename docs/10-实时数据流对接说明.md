# 实时数据流对接说明

> 2026-09-19。给**接生产数据源的人**看:要把 mock 换成真实行情源，需要对方提供什么、我们这边改哪里。
> 协议定义见 `09-实时行情管线契约.md`，本文只讲**对接**。

## 0. 一句话

```
生产者 → WS 网关 → SharedWorker → 主线程(每500ms拉) → 虚拟表格
        ↑ 你要对接的是这一段
```

浏览器侧（SharedWorker 往右）已经做完且压测通过，**对接方只需要满足网关契约**，前端一行不用改。

---

## 1. 全链路数据流

```
┌─────────────┐   ①报价产生
│ 行情源       │   OT推送 / QT / 经纪商 / 做市商
└──────┬──────┘
       │ 每条分配单调 flow_id，写 quote_flow，upsert quote_latest
       ▼
┌─────────────┐   ②按组缓冲 200ms，窗口内同券只留最大 flow_id
│  WS 网关     │   {op:'batch', group, sendTime, items:[QuoteDelta]}
└──────┬──────┘
       │ 一条 wss 连接，permessage-deflate
       ▼
┌─────────────┐   ③按 groupName 累积，同券覆盖，背压 5000/组
│ SharedWorker │   跨标签共享：10 个标签页只有 1 条连接
└──────┬──────┘
       │ MessagePort，主线程**主动拉**（不是推）
       ▼
┌─────────────┐   ④每 500ms 一次 PULL；document.hidden 时停拉
│  主线程       │   收到 Map<group, QuoteDelta[]>
└──────┬──────┘
       │ 按 bond_uni_code 原地 upsert，只标脏变化的格子
       ▼
┌─────────────┐   ⑤虚拟滚动，只渲染视口 ±10 行
│  表格         │   DOM 恒定 ~29 行，与总量无关
└─────────────┘
```

**四层削峰**，这是 300 条/秒只花 3.8% CPU 的原因：

| 层 | 手段 | 效果 |
|---|---|---|
| 网关 | 200ms 成批 + 同券去重 | 300 条/秒 → ~5 批/秒 |
| Worker | 按组累积 + 同券覆盖 | 多条更新塌缩成 1 条 |
| 主线程 | 500ms 主动拉 + 隐藏暂停 | 渲染频率与消息速率解耦；后台标签零消耗 |
| 渲染 | 虚拟滚动 + 单元格级闪烁 | DOM 与数据量无关 |

## 2. 对接方要提供什么

### 2.1 必须有：逐行单调版本号

这是**唯一的硬要求**。每条报价必须带一个全局单调递增的 `flow_id`（int64）。

没有它会怎样：
- 乱序到达时新价被旧价覆盖
- 重复投递会变成重复行
- REST 首屏与 WS 推送无法收敛到同一状态

如果源系统没有这个字段，在网关层分配（我们 mock 就是用 SQLite 的 `AUTOINCREMENT`）。**不能用时间戳代替**——同毫秒并发会撞。

### 2.2 必须有：行身份键

`bond_uni_code`（我们用 windcode）。**同一只券的新报价是同 key 新版本，不是新行**。

### 2.3 消息形态

网关发给浏览器的每条消息：

```jsonc
{ "op": "batch",
  "group": "bond-type_中票",      // 该批属于哪个订阅组
  "sendTime": 1758270000123,      // 服务端发出时刻(ms)，用于算端到端延迟
  "items": [
    { "f": 10293847,              // flow_id  ← 行版本，必填
      "u": "102584288.IB",        // bond_uni_code ← 行身份，必填
      "t": 1758270000100,         // issue_time(ms)
      "bb": 2.2472, "bbv": 3000, "bbs": "国利",   // 最优bid 价/量/方
      "bo": 2.2372, "bov": 2000, "bos": "中诚",   // 最优ofr 价/量/方
      "fm": "实盘", "cl": "+1", "st": "询价中",
      "ib": 2.2872, "ibv": 5000, "io": null, "iov": null }
  ]}
```

**只带动态字段。** 券简称、评级、期限这些静态列不要放进推送——几十万条/天，每条多带 200 字节就是一天 60MB 白跑。静态数据走 §2.5 的接口，Worker 缓存后在客户端 join。

字段名用缩写不是炫技：`best_bid_vol` → `bbv` 每条省约 60 字节。

### 2.4 订阅协议

浏览器 → 网关：

```jsonc
{ "op": "sub",   "groups": ["bond-type_中票", "bond-tenor_1to3"] }
{ "op": "unsub", "groups": ["bond-type_短融"] }
{ "op": "ping" }
```

**组名即筛选维度**，规则见契约 §3。核心约定：

- 订阅是**并集**：订了哪些组就收哪些组的数据
- 列表筛选是**交集**：选「中票 + 1~3Y」要的是同时满足
- 两者语义不同是本来面目 —— **订阅负责把流收窄到超集，列表 REST 按完整谓词收紧**

未订阅任何组时不推任何数据。

### 2.5 配套 REST

| 接口 | 用途 | 频率 |
|---|---|---|
| `GET /api/bond-static/all` | 静态主数据全量，Worker 启动拉一次并缓存 | 每次建连 1 次 |
| `GET /api/bond-static?codes=a,b,c` | 缓存缺失时按需补 | 很少 |
| `GET /api/bonds?groups=&before=&limit=` | 首屏与翻页，keyset 游标 | 翻页时 |

**翻页必须用 keyset（`before=<上页最后一条的 flow_id>`），不能用 offset。** 头部不断插新数据时 offset 会整体右移，翻页会重复取到已见过的行——我们实测过，滚 4 次只拿到 197 条而不是 200 条。

## 3. 我们这边要改什么

换真实数据源时，**前端零改动**。只需要：

| 位置 | 改什么 |
|---|---|
| `web/src/lib/quoteClient.ts` | `createQuoteClient({ wsUrl, staticBase })` 指向真实网关 |
| `mock/` | 整个替换成真实网关，或保留作离线演示 |
| 契约 §3 的组名 | 与对方的订阅维度对齐 |

如果对方的字段名和 §2.3 不一致，**只在网关层做一次映射**，不要让缩写形态渗进浏览器——那是唯一按量计费的一段链路。

## 4. 降级与异常

### 4.1 SharedWorker 三级降级

目标环境有国产化浏览器，不能赌 `SharedWorker` 一定可用：

| 级别 | 条件 | 代价 |
|---|---|---|
| `shared-worker` | 首选 | 多标签共一条连接 |
| `worker` | SharedWorker 不可用 | 每标签一条连接，但 WS 不占主线程 |
| `main-thread` | Worker 也不可用 | 每标签一条，WS 在主线程，保留 500ms 缓冲语义 |

判定标准不是"构造没抛异常"，而是**构造后 8 秒内 Worker 是否真的回话**——某些浏览器有构造函数但是空壳。当前级别可从 `quoteClient.stats().transport` 读出，埋点面板上直接显示。

### 4.2 断线重连

指数退避 1s → 2s → 4s → 上限 15s；重连后按引用计数**自动补订**已订阅组，业务代码无感。

### 4.3 背压

Worker 侧每组窗口上限 5000 条，超出**丢最旧**并累加 `dropped`。

为什么丢最旧不丢最新：行情是**状态量**不是事件流，用户切回来要看的是每只券的最新价；丢最新会让界面显示过期价格，那比丢几条中间过程严重得多。

`dropped > 0` 会在埋点面板变红。持续 >0 说明网关推送速率超出了消费能力，要么加大批次间隔，要么收窄订阅组。

## 5. 验收指标

改造后实测（本地 mock，Chromium，1600×950）：

| 指标 | 300 条/秒（峰值） | 10 条/秒（日常） |
|---|---|---|
| CPU | **3.8%** | **2.1%** |
| 样式重算 | 0.40% | 0.08% |
| 渲染 DOM 行数 | **29（恒定）** | 29 |
| JS 堆 | 10MB（不增长） | 10MB |
| 长任务 | **0 次** | 0 次 |
| 全选 / 取消 / 勾单行 | 45~84ms | 同 |
| 后台标签 | 隐藏 8 秒内**零消耗** | 同 |

对接真实源后，**用同一套埋点复测这张表**。任何一项明显劣化，先查：

1. 网关是不是真的在成批（看 `sendTime` 间隔）
2. 是不是在推静态字段（看单条消息体积）
3. 是不是没去重（看同批内同 `u` 是否重复）
