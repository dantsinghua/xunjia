# 询价整改：最小架构设计挑战稿

安琳，推荐保留 Vue + Python 的现有边界，收敛为**一个业务核心、OSS/邮件两个传输适配器、一个事务存储**。本稿供主审整合，属于设计建议，尚未实施或验收。

本次只读复核评审与关键命令/Dify路径，没有修改源码、业务数据或测试，没有访问真实账户。本报告为新增设计交付物。

## 已确认条件

- 5 人各使用自己的 1 个企点账号，固定账号所有权；不建立通用席位转让、多人审批或新的身份体系。
- 人工确认询价批次和策略后，可在已确认边界内自动谈价；拿到实价转人工。模型仅做意图与结构抽取，确定性规则决定价格和动作。
- 同对手允许多券并行；只有唯一归属的消息可以自动处理，歧义转人工，不能用最近一条强行猜券。
- OSS 和邮件必须本期完整双向交付。每绑定择一主用，由人工切换；unknown 先对账，不能以切通道代替对账。
- 登录参考 /home/anlin/work/qtrade/ibquote，OceanBase 主数据接入沿用该项目，具体源码证据由主审核查。本分支未复核其接口、驱动或数据库模式，不根据旧数据库文档猜方言或声称已验证生产事务。
- 已上传的信封可能晚到，已提交给企点的消息不能承诺撤回。设计必须明确停止的生效边界。

## 推荐结构与最小边界

Vue/REST → 既有登录与固定账号归属 → Python业务核心 → 事务库中的会话、事件和命令 → 当前主用的OSS/邮件适配器 → 采集执行端共同命令账本 → 企点。

查询视图只读业务结果，不执行模型或发送。后台消费属于同一代码库和业务部署，可先与API同进程管理生命周期；若API开多个进程，必须明确唯一逻辑消费者归属，不能每个进程都起收发循环。不引入Redis、Kafka、独立规则微服务或通用调度平台。

数据库连接与迁移方式复用经主审核实的现有机制；询价业务表独立于主数据表。不能因存在OceanBase主数据接入，就默认获准在主数据源表写询价状态；也不同时维护SQLite/MySQL/GaussDB多套生产方言。

为什么不能只修几个if：当前 imlink/dify_inquiry.py:263-279 在发送时重新读取当前账号；331-398 在模型前查暂停、返回后直接发；imlink/commands.py:148-149 不允许失败结果被迟到成功纠正；监控GET仍驱动处理（mock/mock_server.py:978-1015，imlink/dify_inquiry.py:542-553）。这些问题跨越授权、执行和送达事实，进程内锁不能消除邮件/OSS/RPA的提交空隙。

## 最小持久实体

逻辑上六类业务实体，加收信游标元数据。不是追求表数最少，而是每项只保存一种不能丢失的事实。

| 实体 | 最少保存的事实 | 必要约束 |
|---|---|---|
| account_binding | 固定owner_user_id、稳定企点号、工作台、主用传输、binding_version、账号自动运行开关 | 复用既有用户ID；账号不可重复归属；单绑定一个主用传输；凭据使用已有安全配置引用 |
| rfq_batch | 人工确认人/时间、账号快照、券和收件人集合、确认策略、请求幂等键 | 确认后不可偷偷修改；改边界形成新版本并重新确认；不另建审批流 |
| conversation | 账号+会话类型+对手、自动/人工/暂停模式、control_version、交回后的入站水位 | 固定账号决定操作者；一个对手可有多个券会话；整段接管范围明确 |
| rfq_session | batch/conversation、券、BID/OFR、有效策略、已确认报价/轮数、是否问过量、业务状态、version、pending_command_id | 不再只按券全局保存；同对手多券合法；同账号同对手同券同方向的重复活跃意向须显式合并或冲突 |
| event | 入站原文、回执、人工控制、规则决定的不可变事实；稳定event_id、账号/peer、来源、时间/序号、关联ID | 入站去重与处理结果事务提交；审计只增；处理状态可为独立元数据，不要求完整事件溯源框架 |
| command | 稳定command_id、不可变正文及摘要、账号/peer、关联会话、策略/控制版本、授权人、执行状态、有效期、尝试信息 | 业务幂等键唯一；同key不同内容冲突；合并报价可关联多券；人工发送也经此出口 |
| 收信游标元数据 | 每绑定、每传输的持久读取位置/代次 | 与入站落库同事务；邮件UIDVALIDITY变化不能沿用旧UID；OSS按稳定事件序号或对象标识处理，不把翻页token当永久业务序号 |

策略快照直接保存在批次/会话中：价格基准、方向、起始、边界、步幅、量、估值/估值日、有效期。BP与绝对收益只能有一个有效模式，缺换算输入时不得自动决策。不拆出通用策略服务和复杂配置继承。

回执是event的一种，不先建回执微服务。命令聚合状态与回执事实分开，迟到/冲突证据都保留。业务状态与outbox同库同事务，不做跨库业务事务。

执行端必须有自己的持久命令账本：command_id、正文摘要、执行状态、企点出站标识、取消墓碑。外部副作用发生处的去重事实不能由后端command表替代。

## 最小业务事务

1. 确认批次：后端解析最终券/收件人集合，给出可复核清单和策略；确认事务核验用户、固定账号归属及版本，冻结批次/会话，写首轮command。未加载的前端窗口不能冒充全选。
2. 接收入站：适配器统一信封，按稳定event_id去重落库，再推进游标。所有消息可展示；历史导入、未授权会话不自动回复。
3. 理解和决策：模型调用在事务外，只抽取。任务携带账号、conversation/session、控制版本和入站ID。返回后重新核验，唯一归属且仍授权才进入规则。
4. 生成回复：事务同时保存入站处理结果、规则判断、待执行动作和唯一command。重试同一入站不能产生第二个业务动作。实际轮次和已发价格在发送确认后推进，不能写出outbox就视为已经发送。
5. 投递确认：worker短事务认领后做I/O，不在网络等待期间持有数据库事务；回执事务更新command/session及审计。
6. 实价/歧义转人工：歧义消息不进数值规则；整段会话接管时其他券自动回复一并暂停，界面显示范围；交回保留不可回退入站水位，不补答旧消息。

同对手多券无需先建设L1-L5插件系统。第一期用明确代码/唯一简称、可信引用、唯一活跃会话等确定依据；模型映射必须落在当前已授权候选集合中。价格区间或时序不能唯一证明归属时转人工。后续是否扩大自动归属以样本证据决定。

## 发送状态：六种足够

| 状态 | 含义 | 允许动作 |
|---|---|---|
| queued | 已授权落库，未开始外部投递 | 可取消；投递前复核权限、停止、版本、期限 |
| pending | 已开始一次投递，无明确执行结论 | 同command_id对账；不能显示已发出 |
| unknown | 超时或崩溃，不能确认是否执行 | 冻结相关会话后续自动报价并对账；不换ID/通道盲发 |
| sent | 执行端确认真实企点出站，有可核对证据 | 重复回执无副作用 |
| failed | 明确未执行或被拒绝 | 按原因修复；正文/策略变化须创建新的已授权业务命令 |
| cancelled | 证明尚未执行且已取消 | 迟到旧信封不能重新执行 |

OSS PUT成功、SMTP接收成功、目录在线都只是传输事实，不是sent。界面宜写“已发出（执行端确认）”；没有对方接收证据时不宣称对方已送达。

pending在外部I/O前持久记录：如果标记后、投递前退出，会多一次对账，但不会假装副作用肯定没有发生。传输尝试作为元数据/事件，不增加一串SMTP_OK/OSS_OK业务状态。

unknown可在新证据到达后转sent或failed/cancelled。冲突回执不能任意最后写入获胜，要保留事实并转人工核对。执行端若在点发送后、保存成功前崩溃，恢复时不得再次点发送；先用出站标识/可信关联核验，核验不了保持unknown。

对于非事务性RPA，不承诺数学上的exactly-once。兑现的是：不盲目重复执行、结果可核对、未知不冒充成功或失败。

## 双通道协议与人工切换

共同业务信封至少包含：协议版本、event_id/command_id、workbench_id、account_uid、session_kind、peer_id、关联会话、正文摘要、创建时间、有效期。授权与回执身份绑定这些字段。复用已有加密/认证能力，不新增第三套自创密码协议。

- event_id由采集端首次持久记录时确定，两种传输保持一致。不能仅用正文哈希，因为同一句话可以合法出现两次。
- 邮件Message-ID、IMAP UID、OSS对象名只用于传输定位，不替代跨通道业务ID。
- command_id在确认批次/规则生成命令时确定，后端、传输和执行端重试不变。两传输共用执行端去重账本；同ID不同摘要拒绝并告警。
- 每绑定仅一个主用传输；未投递queued可在人工切换事务中改投新主用，pending/unknown不能随配置无声迁移。
- 切换前停止新增投递，先核对未决命令；旧通道保留迟到回执及切换前入站事件的读取，直到约定水位排空，不继续成为第二个发信通道。旧通道无法排空时明确切换未完成。
- OSS、邮件分别验收双向消息、断点重收、取消控制和回执。relay/mailbus.py:39-52的文件直投只是测试替身，不是邮件交付。

## 停止中/屏障：最小可兑现口径

后端停止成功与执行端停止确认必须区分。当前规模无需通用分布式授权租约，可采用**固定命令集合的取消屏障**。

### 后端事务先封口

停止目标明确为账号、批次、券会话或整段对手会话。事务更新停止/控制版本，冻结范围内全部尚未终结的command_id。

命令生成和投递认领都检查同一控制记录，与停止事务有明确串行顺序：停止先提交，旧模型结果/新认领拒绝；命令先提交，则该ID必须进入屏障集合。不能只用实例线程锁保证这条规则。

尚未开始投递的queued可直接取消；可能出本机的命令形成控制信封：
cancel_barrier(barrier_id, target_command_ids, scope_version)。
屏障走当前主用传输，重试保持barrier_id。

### 执行端持久取消墓碑

执行端记录全部command_id的取消要求，**尚未收到原命令的ID也要记录**。旧邮件或OSS信封晚于屏障到达，仍被拒绝。

统一串行化最终发送前检查与取消登记的临界点：未执行者cancelled；已完成者sent；正在执行的窄临界区等待结束后返回证据，不为赶停止而杀到一半、再当作未发送。

回执逐命令给cancelled/sent/unknown，并确认屏障持久生效。如命令集合需分片，收齐全部片确认才完成，不能第一个ACK就认为整批停止。

### 用户看到什么

- 点击后：**已停止新增，正在确认在途消息**。
- 执行端不可达：**停止中／执行端未确认**，显示待核对数量；后端不再生成/投递新的目标回复。
- 完整屏障确认：**已停止新发送**；已经发出的仍列已发出，unknown仍列待核对，不能伪造取消成功。
- 保证范围：屏障执行端生效后，不再为被覆盖的旧命令启动新发送动作。不保证撤回已提交企点的消息，也不保证已提交消息不会稍后在对方页面出现。
- 人工接管后的手工发送仍经共同command出口；旧机器人命令有unknown时先对账，不在同一语境盲目继续。

合并多券正文的单条命令中若一券被停止：未执行时取消整条，再按仍获授权的剩余券生成新命令；必须先证明原命令未执行，unknown时不能改正文/ID。已发合并消息不可局部撤回。

执行端共享账本与cancel_barrier是跨仓库交付依赖。仅改本仓库HTTP服务不能兑现。缺失时只能如实显示“本地停止新增，远端未确认”，不能宣布完整停止验收通过。

## 固定账号所有权

- 复用可信登录user_id；前端operator/user字段不能决定权限。
- 普通用户仅能确认、停止、接管、改策略、手工发送及切换自己的账号。读取沿用既有项目角色；未获得共享授权前不默认互看全文聊天。
- 同用户两浏览器共享业务事实；确认用幂等键，控制/策略用版本比较，过期版本返回冲突，不自动覆盖。
- 不设计借号、席位转让、主管代操作或通用审批。既有管理员紧急停止权限如已存在则复用并审计，不凭此新增管理员外发权限。

## 不可省的复杂性

| 内容 | 原因 |
|---|---|
| 完整账号/会话身份、固定所有权 | 切号和并发不能改变任务身份 |
| 授权策略快照、控制版本、事务outbox | 确认、停止、模型结果必须有一致先后 |
| 执行端跨通道去重账本、取消墓碑 | 后端去重无法约束晚到信封和真实UI副作用 |
| unknown及证据对账 | 外部发送和本地落库不能原子提交 |
| 多券唯一归属、不确定转人工 | 同对手多券并行的安全条件 |
| 持久游标、事件去重、审计和恢复验收 | 两传输都会延迟、重投、断点恢复 |

## 可删或不引入的复杂性

- 微服务、独立消息中间件、通用工作流平台：同业务服务+有界任务+事务表足够。
- 多人席位/转让/审批：固定5个user→企点账号映射。
- 两通道自动同时发送/自动故障转移：单主用、人工切换、先对账。
- policy服务、配置继承树：已确认批次的不可变策略快照。
- GET内线程、多个JSON真值、前端永久状态覆盖：后台消费与统一查询。
- 完整事件溯源/CQRS框架、插件式L1-L5引擎：事务状态表、只增审计和明确归属证据。
- 先迁移全部数据库、同时适配多种数据库：复用已经证实可用的客户接入方式。

## 五个最危险场景与验收

| 场景 | 故障注入 | 必须证明 |
|---|---|---|
| 1. 停止与模型/外发/晚到信封竞态 | 模型返回前停止；认领后停止；原邮件晚于取消屏障；执行端离线 | 停止事务后不新增目标命令；此前命令全部进入屏障；晚到旧命令被拒；未确认不显示完整停止；已发不伪造取消 |
| 2. 发出后ACK丢失，再人工换通道 | 点发送后、保存成功前崩溃；丢ACK；OSS→邮件切换；重复command_id | 不再次点发送；unknown先核对；迟到证据可修正；同ID不同正文冲突；不靠换路/换ID重发 |
| 3. 同对手两券模糊回复与跨账号同ID | 两券等待，只回“1.8出”；另一账号相同peer/message ID；两次同文新消息 | 歧义转人工不串券；账号隔离；清晰券锚独立推进；正文去重不能吞掉合法新消息 |
| 4. 双浏览器重复确认、过期策略与越权 | 同用户两页同时确认；一页改边界、另一页提交旧版本；其他用户伪造account | 一次业务命令；旧版本拒绝；按确认快照执行；越权在查敏感数据/生成命令前拒绝并审计 |
| 5. 双通道重复入站、游标重置、跨日旧任务 | 同事件经旧/新通道到达；落库后游标提交前崩溃；UIDVALIDITY变化；昨日命令今日才到 | 一事件一个业务动作且不漏消息；过期旧命令拒绝；新日估值/有效期/首句确认按已确定规则处理，不沿用旧报价盲发 |

全部先用假OSS、假IMAP/SMTP、假执行器覆盖真实入口与持久重启，不能只测辅助函数。两传输再分别完成有授权的真实环境验收；本稿不授权外发。

## 反方、张力与综合

**反方最强论点**：只有5人，单进程全局锁加JSON即可；outbox和取消协议看似过度设计。

**张力**：全局锁只解决本机并发，不能跨越OSS/邮件/RPA崩溃边界；追求自动故障转移和绝对一次发送反而增加复杂性、掩盖未知结果。

**综合**：保留一个服务、固定账号、单主用通道与一个事务库；只增加直接约束外部副作用的身份、账本与屏障。RPA结果未知时暂停核对，不继续叠加自动重试层。

## 主审需补齐的证据

1. ibquote实际登录入口、稳定user_id、已有会话/权限/CSRF口径及账号归属关系。
2. 询价业务表可使用的数据库/Schema、OceanBase实际模式/驱动/迁移机制；主数据接入不是写源表授权。
3. 采集端共同event_id、执行账本、出站关联证据、取消屏障和有效期检查；缺失即双向交付依赖。
4. 邮件收发方式、认证、轮询/通知能力、附件尺寸和实际延迟，以确定承载与有效期，不能按PoC假定生产能力。
