## 一、执行摘要与证据边界
已使用实际 InquiryService / ChatRunner / Dispatcher / FastAPI API 和合成 SQLite 数据完成 22 组业务反例探针，全部执行完成。探针拦截意外网络连接：0 次网络尝试、0 次真实 IM/OSS 发送、0 个遗留临时数据库目录，15 个相关源文件运行前后哈希未变化。
这些结果证明的是“给定原文及结构化候选，当前后端会如何处理”，不是实际模型解析准确率，也不等于真实 Dify/OSS/采集端 E2E 已通过。部分结果属于确定缺陷；意向价能否还价、数量继承、整会话停止等属于需要业务裁决的规则。
最重要的结论：系统将消息事实提取、询价策略决定、回复文本校验与外发资格耦合在一个回合中，缺少独立的报价事实账本。多券、多边、分条补量、改价、撤价及人工模式下持续分析因此无法完整闭环。
现场只读检查：Dify API 容器运行；本机询价应用 8855ccb7-ce8c-40d0-b5cb-bca6e30c1fc2 为 advanced-chat、31 节点草稿，未发布；两个主要 LLM 节点均仍要求 observations=[]。QTradeWinAgent 当时为 Stopped / Manual，OceanBase 测试容器为 Exited。本报告不把这些服务当成全链路在线系统。
## 二、实际数据流：Dify 不直接访问 OSS，也不直接操作业务库
当前源码路径：
    对手企点消息
      → 采集端原生消息日志 / native_id
      → OSS 事件对象及 manifest（水位）
      → xunjia Inbox.poll/apply
      → xj_message 原文入库
      → ChatRunner 读取会话和询价快照
      → Dify /v1/chat-messages
          → 当前自定义模板通过 HTTP 节点回调 context / history / validate
      → AgentTurn 候选
      → xunjia 校验和提交
      → xj_session / xj_turn / xj_command
      → Dispatcher → OSS 命令对象
      → 采集端接收账本 → 原生发送
      → OSS 回执 / 原生回流
      → xunjia receipt 更新数据库
      → 前端监控轮询 API
必须保持的区别：消息已入库 ≠ 报价已解析；Dify 回答完成 ≠ 候选已经发出；OSS PUT 成功 ≠ 企点已发送；返回 HTTP 200 ≠ 业务分析完整。
相关代码：server/inbox.py:19–48、51–92；server/chat_runtime.py:327–418；server/runtime.py:38–100；server/transports.py:238–257、382–455；relay/collector_bridge.py:79–125、142–189。
已做对的部分应保留：显式预览确认、Decimal 收益率边界及有符号价差、BP 可信快照重核、同事件与命令的幂等、OSS accepted 与原生 sent 区分、结果未知时先对账、公开 Tool 免 Token。不要为整改再次引入长期 AK、Dify 管理员依赖或公开 Tool Token。
## 三、确定缺陷与未闭环
### F01：0.15.3 兼容模板主动禁止报价解析，不是版本能力限制
scripts/build_dify0153_dsl.py:22–31 将 observations 固定为空，禁止 COUNTER、ASK_QUOTE，交易消息只能 WAIT 或转人工。实际本地 Dify 草稿也含这些限制。
这是一项此前模板生成阶段添加的功能降级，不是用户确认的完整业务需求，也不能推导成“Dify 0.15.3 无法用 LLM 输出结构化报价”。画布白屏修复和该业务缺口是两件事。
修改意见：先确认现有客户应用的输入输出合同，使用其支持的 LLM/工作流节点执行结构化解析。把“能解析”与“是否准许生成还价建议”分开定义。不得用 observations=[] 冒充只读分析。对于已有发布应用，后端适配其 API 合同，不需要管理后台权限。
### F02：别名正确命中 B，却仍可能套用 A 的旧焦点
server/chat_runtime.py:151–168 同一消息只选一个 selected；已有 active_bond_session_id 优先于某些别名证据。_enrich 已把 B 别名解析为 bond_mentions=[B]，但 _check 只用它排除“非在谈券”，不把唯一 B 候选用于归属。
探针 B12：先谈 A，再发 B 的唯一别名。错误归 A 的观察被接受，正确归 B 的观察被拒绝。
修改意见：按文本片段分别进行券识别和归属；保存候选、匹配来源、明确度及证据。明确代码/唯一字典别名与旧焦点冲突时，不能沿用旧焦点。焦点是省略时的参考，不是覆盖新证据的权威。真正有歧义应保存候选、请求澄清，而不是猜一只。
### F03：同一条消息多券、多边，当前数据结构和校验均不支持
server/chat_runtime.py:152–154、190、196、251–252 依赖单一 selected；双向报价直接拒绝；每回合至多一个公开行动。
探针 B01/B02：两只明确代码的报价被拒绝；同券 bid/收量 与 ofr/出量并存也被拒绝。不能用“有 observations 数组”认定已支持多券，因为数组中的每项仍被要求属于同一个 selected。
修改意见：一条消息可解析出多个 bond × side 的 observation。每条分别携带价格、数量、实价程度和证据；是否拆成一条或多条外发，是另一项发送策略。不得让一个条目的歧义吞掉其他已明确条目。
### F04：原文数字未按角色分类，数量可能被当成收益率
server/chat_runtime.py:170–207 对整句提取买卖词、数量和小数，没有先确定文本片段、说话人及单位。
探针 B03：2.20，0.5亿 被当成两个价格而拒绝；补成 2.20%，0.5亿 则通过。即使业务对“无百分号是否可继承收益率口径”尚未决定，0.5亿也不该进入收益率候选集合。
修改意见：提取价格/数量/日期/期限等带角色数字，优先使用单位及所在语句。保留 raw_value、raw_unit、normalized_value、basis 和原文区间；“你收”“我出”“有客户收”还应区分报价主体，不是任意出现收/出都代表对手本人当前实盘。
### F05：出量、收量、实价状态和报价版本没有完整事实账本
server/chat_runtime.py:193 只要求 firm 为 bool，214 构造的落库 quote 不含数量；374–418 没有持久化 trader_view；server/routes.py:175–179 的 theirVol 固定为空。
探针 B11：即使候选有 volume_wan，落库仍丢弃；trader_view 中的分析依据没有保存；明细接口对方量为 null。
探针 B06/B16：原文明说不是实价时，把 firm 错标 true 的候选仍能通过；后来单独补一句“刚才只是意向”，旧 firm 仍然是 true。
修改意见：价格、买方量、卖方量、实价程度、交割条件等都应可独立更新。报价历史追加保存，当前视图由有效版本派生。实价至少需要 firm / indicative / unknown，而不是用 false 混淆“明确意向”和“未说明”。firm 状态变化必须能够引用原价，而非强制再次重复价格数字。
### F06：停止发送与停止分析混成一个开关；价格与数量分条无法合并
server/app.py:68–83 和 server/chat_runtime.py:54–64 要求 AUTO、bot、social 开启且无任何在途命令才启动解析。ingest 会把人工/停止状态消息置为 ignored。
探针 B08/B09：人工接管后有真实新报价不解析；等待发信回执时也不解析。
探针 B04：对手先发报价，再发数量；即使两条都已经入库，第一条因为无量转人工，并把后面的数量置为 ignored。
修改意见：分离接收、只读分析和自动动作许可。原文接收和可用事实提取不应被“上一条外发等待回执”阻塞。分条补充信息建立未完成事实槽位与上下文引用；聚合窗口和数量继承规则由用户确认。人工模式是否继续只读分析也要明确，但不等于重新打开机器人发送。
### F07：对方已更新价格甚至已到目标，旧模型结果仍可外发
server/chat_runtime.py:31–46 检查控制版本、会话修订和记忆版本，却没有普通新报价的消息水位/事实版本；server/runtime.py:63–70 也只检查这些旧条件。
探针 B10：模型根据2.20报价生成候选期间，对手改为2.18；旧候选照常提交并被模拟执行。
探针 B22：新实价改为2.60，已满足现有 BUY 边界2.40的到价规则；旧2.48候选仍被模拟发送，新消息仍在 queued。
修改意见：每条候选绑定 source_message_ids、相关 quote_revision、context_revision 和待分析水位。提交及实际发送前重验依据是否被同券改价/补量/撤价覆盖。尚未发送的旧候选应重新判断；已进入原生发送、结果未知的命令不能假装撤回成功或直接重发。无关闲聊是否作废候选，应由解析后依赖关系判断，避免所有消息都无差别中断。
### F08：一个公开措辞错误，会把正确解析出的报价一起丢掉
server/chat_runtime.py:374–384 只有在最终措辞与候选均通过时才更新 peer_quote；失败后 _fail 将整轮失败并转人工。
探针 B18：对方2.20报价解析正确，但模型把建议2.48的公开句子写成2.49。外发拒绝是合理的，然而对方报价也未落库。
修改意见：原始候选、字段核验、有效市场事实和回复决策分开持久化。拒绝不一致外发，不应删除已经单独核验的对方事实。未核验的模型输出只能保存为“待核对候选”，不能直接冒充有效价。
### F09：上下文只支持附带摘要，不支持完整的报价证据链
server/chat_runtime.py:86–98 提供全对话最近30条和一个焦点；191–199 要求 observation 只能引用本条消息且价格数字必须出现于本条原文。history 为整对话一次补取，不等于每券上下文状态。
探针 B21：对方说“就按你这个价，1000万”，即使上一条原生已发价2.48在上下文中，后端仍因本句没有价格数字拒绝引用。
修改意见：允许受控的跨消息 evidence_refs，分别记录价格、数量、方向、实价的出处；只可引用实际收发事实，不把 Dify 历史候选当作已发送价。隐含接受是否属于成交意图、是否仅显示待人工，应由业务确认，不可默认执行成交。
### F10：单券按钮作用到整个对话，但 API 仍报告只停了所选券
business.stop_sessions:604–621 会因同对手合并指令而停止整个 conversation；retract/edit:499–505 同样对整个对话转人工。
探针 B13：请求仅停 A，返回 stopped=[A]、count=1，实际 A/B 都 STOPPED。
探针 B14：只撤回 A 报价，B也HANDOFF；A原消息虽 revoked，其当前 peer_quote 仍留存。
修改意见：区分“取消包含多券的物理命令”与“终止全部逻辑询价”。API 必须返回真实 affected_sessions/affected_bonds。若业务选择整线程暂停，界面必须明确提示范围；若选择按券暂停，其他券应保留状态，未决共享消息先核对再生成新命令。
### F11：命令终态、报价有效性和前端展示不一致
business.receipt:397–404 对非sent提前返回；runtime:71–73取消过期命令后不收尾会话。market.aggregate_sessions:37–44只覆盖failed/unknown，cancelled未对应清理。
探针 B15：failed或cancelled命令仍留下WAITING_SEND和pending引用；过期取消在前端仍显示“待回执”。
server/routes.py:96–103 返回旧报价和固定freshness；没有按当前时间重算，也不核对原消息是否撤回。
探针 B17：601秒后的报价仍显示“本轮对手消息”，并继续展示价差。数据库接收事实、解析状态、有效报价与外发状态不能共用一个含糊的“已落地”状态。
修改意见：独立的命令终态收尾；当前报价视图按撤回、替代、过期状态更新，保留历史；前端显示接收/解析/澄清/有效/失效/决策/发送阶段，不再把轮询成功当事实有效。
### F12：Dify合同、历史编排、可观测性仍分散
DifyChatClient/server/dify_client.py:62–107允许50条observations；ChatRunner:135–140只允许10条。Dify/client支持4000字公开文本而业务只允许1500字。node_code中历史条件数量与后端也有不同边界。
探针 B19：11条观察通过客户端却被后端拒绝。
process只发送turn_ref等定制输入并要求严格AgentTurn，不是任意已有Chatflow填Key即可接入。当前仅有chat-messages，不能把Workflow Key当成Chatflow Key使用。
node_code.prepare_context:65–67仍强制要求旧tool_budget_ref，但公开Tool已经免票据。这是尚未清理的合同耦合，不是公开Tool仍要求Token。
Dify流式响应在客户端聚合完成才返回；task_id、message_id、workflow_run_id虽在ChatResult存在，业务提交主要保存conversation_id，缺少贯穿节点失败到前端的一致追踪。trader_view也丢失。
修改意见：一个版本化的输入输出schema生成客户端、Code节点和后端校验；选择唯一历史编排方；保存每轮解析与决策状态及Dify运行标识。进度事件不是把不完整的流式JSON当真值或直接发送。
### F13：采集端端到端仍未接线，OSS路径相同不代表协议一致
Windows宿主仍通过 src/qtrade_agent/app.py:49、384–386、420–422、939–945 使用旧XunjiaInbox；没有看到当前v2 CollectorBridge/ReceiverLedger/QTradeNativePort在宿主入口实际装配。
旧inbox回执为cmd_id/ok/code；xunjia v2读取的是带命令身份和native证据的receipt信封。两边使用相近乃至相同的wb/.../in/xunjia与ack目录，会产生旧消费者读到新对象的协议冲突风险；这是源码兼容性结论，本次没有向真实桶写对象做复现。
新Bridge原生消息映射 normalize_native_message 默认输出 kind=message，采集端撤回/编辑事件仍需逐条确认实际支持，而不是以业务后端有retract分支认定现场会收到。
修改意见：在采集宿主完成v1/v2互斥启停、原生入站挂接、native ID回执、重启恢复与撤回/改价事件接线；使用一致协议版本/来源清单。必须单独验证OSS PUT→原生执行→ACK→DB，不能用两个仓库各自的模拟单测代替。
### F14：前端行情源与Dify分析资料源没有闭合成同一数据合同
server/app.py:33–38 的QB MarketService与47–48的reference_provider是两个入口。后者默认未配置，只支持Python注入；ReferenceDataProvider目前是接口及Unconfigured实现。
因此前端能看见报价，不能证明Dify的bond_info、issuer_info、估值和条款提供者已接通。BP授权服务端快照校验已有正确实现，应保留，但需完成实际数据源适配；不能重新退回浏览器猜估值。
修改意见：定义债券主数据、别名、报价、估值、条款的来源和时点；明确公共行情与对方可成交报价不同。找不到数据时显示字段缺口，不用模型填补。
## 四、需要用户裁决的规则（未自行修改）
Q1. 人工接管、暂停自动发送、等待回执时，是否仍持续只读解析和更新交易员面板？建议拆开读与发，但“停止”具体涵盖哪些动作需确认。
Q2. “实价”的判据是什么？仅明确写实价/firm才算，还是特定对手/场景可继承？未声明应为unknown还是意向？意向价能否产生还价建议、意向到价是否转人工，也要一致决定。
Q3. 数量省略及单位：裸写1000、1000w、0.5亿分别按什么单位/面值口径？可以继承上一条同券同边数量多久？只有价格、随后补数量，是等待补全、只展示缺量，还是立即转人工？
Q4. 多券与双边已经是明确需求，但“一券停止/撤价/转人工”是否影响同对手其他券？出站允许多券合并一条，还是每券独立一条？共享命令未决时的状态提示范围应一并决定。
Q5. 对手在模型生成期间改价/撤价/补量：建议尚未外发的旧候选先挂起、基于最新事实重判；无关闲聊不必无限重启。希望从接收到字段可见/建议可见的最长延迟分别是多少？据此定聚合窗口，不能自设1秒或3秒验收目标。
Q6. “就按你刚才的价”“那只还有吗”等上下文指代允许引用哪些已确认事实？“行/可以/要了”哪些只标待人工核对，哪些意味着停止谈价？本系统仍不执行成交，但解析状态要确定。
Q7. strict_match=false时，对手出500万是否可以继续问900万？本次1000万授权是每个对手的询价上限、每券本轮共享上限，还是涉及累计可成交额度？金额/数量限制不能互相混用。
Q8. 客户最终已有应用是Chatflow还是Workflow？希望Dify负责解析和候选建议，还是已经在其内部编排业务状态？需一个脱敏输入输出例子及字段说明，不需要管理员密码或在聊天中提供Key。当前后端只能直接对接定制Chatflow合同。
Q9. 实际债券主数据、别名、估值和条款从哪个已有资料源读取？估值口径、有效期、跨日续谈规则需要确认。不能因为页面有行情就认为分析工具资料同源。
## 五、建议的业务重构边界
建议仍可在现有应用/数据库内分模块实现，不必为5人场景引入额外微服务。
1. 原文接收层：不可变消息日志、native ID、来源序号、编辑/撤回版本、接收时间。
2. 解析与归属层：一个消息可产出多个“券×报价主体×方向”观察，分别保存字段、单位、证据区间、明确/不明确状态。
3. 报价事实层：当前bid与ofr分开，价格与买卖数量分开，实价状态与有效期分开；事实追加版本，不覆盖抹掉前后文。
4. 策略决策层：只读已核对事实，使用用户确认的授权/到价/步幅/数量规则；记录依据和版本，分析不依赖是否准许发消息。
5. 回复与执行层：候选正文独立校验，提交与发送前重验相关报价版本；native ACK决定是否已发。执行失败不能抹去正确入站事实。
6. 前端投影层：显示来源、时间、bid/ofr量、firmness、有效性、解析进度、决策理由、外发状态；支持增量更新或阶段事件，不把未完成JSON直接当字段真值。
建议事实DTO至少包含：event/message revision、bond candidates/selected evidence、speaker/quote owner、side、price kind/value/unit、quantity value/unit/source、firmness及证据、settlement条件、validity/supersedes、每字段证据引用。
建议决策DTO至少包含：rfq session、依据的quote revisions、读到的消息水位、允许的动作与理由、需人工/澄清事项、对应Dify run IDs。模型草稿与原生已发记录必须分开。
可确定的代码缺陷先补反例和一致性修复；价格/量继承、实价判据、到价转人工和跨券控制规则必须在Q1–Q9明确之后实现。
