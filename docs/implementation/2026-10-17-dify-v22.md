# 2026-10-17 Dify V2.2 A/B 接线与测量

安琳，状态为实施及真实模型初测中，尚未据初测启用生产聚合窗口。

## 当前实现

- 新核心合同入口是 `dify/negotiation_v22`；分别生成 `dify/chatflow_0153/v22-analysis.yml`、`v22-reply.yml` 以及 `chatflow_1171` 同名文件。
- A/B 均为 Start、业务投影、LLM、Code合同校验、Answer 五节点。投影只省机械重复字段，保留全部20条实际原文/ID/方向/日期/证据和授权条件，输出依旧用完整原始快照检查。只接收 `context_json`，每次完整版本快照，无第二套 Dify 会话记忆。阶段输出 schema 为 `2.2`。
- A 输出券关联、分项事实与字段证据、原文连续片段、最终性上下文说明；支持 `corrections` 解决旧歧义/错误归属。程序再次核实数值、归属、版本与证据。Code逐观察保留有效项与错误槽位，不把错误抹成空事实成功。
- B 输出 SEND/WAIT/HANDOFF，公开候选必须经过生产价格、步长、方向、共享量和交易承诺校验。事实事务不依赖B成功；没有在Dify直接写库、发IM或将OSS accepted当sent。
- 公开工具免Token。模型只提出四类 `tool_requests`，Engine实际执行并回传结果，所有工具调用有界。不要求客户Dify管理员凭据，也不需要私有context/history/validate回调。
- 默认 `scripts/build_dify0153_dsl.py` 改为生成V2.2两阶段；旧schema=1只读转换器保留历史回归，必须显式 `--legacy-readonly` 使用，不是当前生产入口。
- `ChatflowClient` 区分超时与网络故障，失败证据不保留前次成功message ID，且只输出固定错误码、耗时和HTTP状态。

## 实际验证边界

本地现有Dify0.15.3实例上创建了本项目专用A/B QA应用并发布。导入前后核对其他应用和模型配置未变，没有重启既有Dify或其他业务。

首个kimi-k2.5请求被既有上游拒绝：401 `invalid_api_key`。没有修改其供应商凭据。另一既有模型qwen3.8-max（来源主机 `token-plan.cn-beijing.maas.aliyuncs.com`）可以实际调用。旧Dify把reasoning_content包装为固定HTML思考区后拼接到结果；已按本机源码确认这一序列化行为并增加回归，只剥离该固定包装，再严格解析单个JSON。

修复后首例真实A+B通过，客户端端到端98,493.882ms。该结果只是一例，不用于生产窗口。

初轮36例使用真实模型与合成对手消息，每例临时SQLite实际执行 `Engine.analyze_thread → 事实事务 → Engine.decide_member → 候选事务`。结果27成功/9失败，未创建IM sender，不能触达真实对手。失败包括4次120秒边界、1次撤价枚举混用、2次澄清复述净价/全价、1次引用方向误拒绝、1次测量脚本将数值等价的5000.0/5000字符串判不等；全部原始记录保留。初轮运行期间核心源文件继续演进，初轮不作为同版终验，也未导出窗口。

最终测量入口已补运行前源码冻结（server/dify/scripts）及哈希清单，独立子进程从冻结根加载，完成后核对冻结根与原工作区漂移。普通高频路径为一券一对手20条双向实际上下文，多券场景独立统计。至少30例事实及回复事务成功才生成窗口配置；失败耗时不进入成功均值。实际无资料源时明确记录，合成估值锚不冒充客户数据。

现有1.17.1镜像内实际graphon schema已验证A/B全部8个节点。验证使用一次无网络、只读临时容器，已移除；既有停止的1.17.1实例未启动。这是实际schema静态验证，不是1.17.1应用导入/模型验收。
