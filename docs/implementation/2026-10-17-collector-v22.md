# QTrade / Xunjia V2.2 采集宿主接口（2026-10-17）

本批按安琳授权定点接线，QTrade 基线为 `f87304bfb1f63482e1d999f6b507a346537c28f7`、分支 `claude/lucid-dijkstra-uu5max`，已有大量未提交改动。本批没有提交 QTrade、启动账号或 Agent 服务、执行 ADB/原生发送、改现场 credentials 或安装包。

## 装配与默认行为

- QTrade `AgentApp.open/start/stop` 装配并管理 `qtrade_agent.ossbox.xunjia_v22.XunjiaV22Host`，复用当前 Agent 的事件钩子与 Bus，不另建常驻服务。
- `XUNJIA_COLLECTOR_VERSION=2.2` 才选择新宿主；未设置仍保持现有 v1 配置行为，未知值拒绝两边发送。V2 显式配置失败不会回落 v1 `XunjiaInbox`。
- V2 读取 `XUNJIA_COLLECTOR_CONFIG_FILE` 私有文件。示例结构如下，示例仅表示字段，不包含真实配置：

```json
{
  "owner_user_id": "REPLACE_OWNER",
  "account_uid": "REPLACE_ACCOUNT",
  "workbench_id": "REPLACE_WORKBENCH",
  "seal_key_file": "/private/path/seal-key.hex",
  "sign_key_file": "/private/path/sign-key.hex",
  "allow_native_send": false
}
```

密钥文件内容为十六进制；相对引用按配置文件目录解析。owner/account/workbench 与接收器、传输发布账本、原生端口固定绑定；已保存 OSS 工作台不一致时拒绝启用。`allow_native_send` 缺省为 false，禁止通过网络命令或 HTTP 载荷注入可执行 guard。

协议组件使用 Xunjia 的 `relay` 和 `server.receiver_ledger`、`server.transports`，仅在显式选择 V2 后延迟导入；未安装时返回 `NOT_CONFIGURED`，不伪造接通。本次源代码跨仓验证不代表既有 QTrade 正式安装包已包含这些依赖，出包方需在干净目标环境确认可导入及完整装配。

## 原生执行许可与水位

Xunjia 下行包含 `business_version="2.2"`、`source_watermark`、`dispatch_watermark`、`control_version`。宿主拒绝旧业务版本进入新发送路径。

1. `ReceiverLedger.execute` 先持久 claim；原生调用与网络 I/O 不持有数据库事务。
2. `QTradeNativePort` 对具体命令作不可变副本，将固定绑定及 `ReceiverLedger.permission(command)` 封成私有 `_xunjia_native_guard`。Bus 不支持该门或缺许可回调时，V2.2 命令拒绝进入原生路径。
3. QTrade Bus 在账号排队和限速等待之后复核。guard 为 false、不可调用或抛异常均为 `GATE_BLOCKED / xunjia_native_permission_changed`，不会调用适配器。
4. 许可通过 `ContextVar` 只在本次发送任务生效；企点 UI 在 `chat_send` 节点/坐标查找完成后、发出原生 tap 调用前再次复核。普通未设置该 guard 的现有命令保持原行为，不受前次上下文污染。
5. 本地许可拒绝由 NativePort 返回 cancelled；原生调用可能已经开始而超时则保持 unknown，不取消 Future 冒充未发送，也不补发。后续只读 QTrade 幂等与原生确认记录对账。

`permission` 是同步本地短事务：检查已存在 pending claim、指纹、有效期、取消墓碑、控制版本、人工 fence、回显 hold，以及尚未取得 source_seq 或超过命令 source_watermark 的入站事件。它不获取 execute 已持有的账号执行锁，不执行模型或网络调用，不把 unknown/sent 改写成可发送。

上述保证是本地最后许可检查；OSS 跨机传播、底层原生执行队列及实际点击不构成跨系统原子事务。已发生的原生发送不能通过后来的取消消息撤销。

## 原文事件、重启与目录

- `Events.on_emit` 在 QTrade 原文已落库后同步调用宿主，回调仅做本地账本与事件队列写入。入站先 `begin_inbound` 再排发布；出向先 `stage_out` 防回显未分类期间自动回复。
- 同一 native_id 的正文变化为 edit，撤回为 retract，二者保留原 message 的 `target_event_id`。本地 outbox seq 防止后续重放旧快照生成反向修改。
- 宿主唯一异步 worker 在线程中执行 Bridge 网络轮询，消息事件、回执、目录使用持久队列。`finish_inbound_journal` 在源事件序号落定后更新水位，再进行上行网络 I/O。
- 重启补传未发布事件，初次安装之前的 outbox 仅作 historical 补取，不伪装新对话。停止发送不停止接收、持久化或解析；完整 Agent shutdown 则停止 worker 并等待在途任务，不假装原生调用可撤销。
- 仅实际装配 guard 链的活跃宿主发布 `negotiation-v22-watermark`。V2 通讯录使用 `wb/{workbench}/out/xunjia/{account}/contacts.bin`，不读写旧共享 `qidian/{account}/contacts.json`；旧 `CatalogPublisher` 继续服务 deposit。
- 正式通讯录 provider 复用当前企点主库旁路只读来源 `list_contact_source_rows` 与现有解码器；读取失败保留先前已发布目录，不填空数据冒充成功，不启动或恢复账号。
